# Reflexion：通过语言反馈改进的语言智能体

## 1. 为什么“再试一次”经常没有用

程序测试失败后，如果只让模型重新生成，它可能改变了代码，却没有理解失败原因；在一个环境里找不到东西，重试也可能重复搜相同位置。重试增加了机会，却不一定增加有效信息。

Reflexion 的主张是：把结果反馈变成一段具体的文字教训，保存在记忆中，下一次尝试带着这条教训行动。基础模型参数不更新，变化的是用于决策的经验上下文。[1，§3]

<a id="s2"></a>

## 2. “语言强化”到底强化了什么

传统强化学习通过奖励优化模型参数。Reflexion 借用“强化”的含义，但主要用语言反馈改变下一次行为。可以把它想象成一个人做完题后写错题本，而不是每次都重新训练大脑。

假设反馈只有“失败”。这条信号很短，却没有方向。反思模块结合执行轨迹，把它展开成“你还没有拿到钥匙，就尝试开门；下次先检查物品状态”。从分数到可行动建议，是它的核心转换。

这也不是简单要求模型“多想一会儿”。必须有一次实际尝试、某种反馈、对反馈的解释，以及把解释带入后续尝试的路径。

<a id="s3"></a>

## 3. 三个角色怎样配合

| 角色 | 接收什么 | 产出什么 |
| --- | --- | --- |
| Actor | 当前任务、环境观察和已有反思 | 文本、代码或动作轨迹 |
| Evaluator | 执行结果或候选答案 | 成功／失败或其他评价反馈 |
| Self-reflection | 任务、轨迹、反馈 | 解释错误并建议改进的文字经验 |

三个角色是功能划分，不要求三个不同的模型服务。Evaluator 也不一定是 LLM：环境成功信号、规则检查、程序执行都可以提供反馈。[1，§3]

算法先生成并评价初始轨迹；若没有完成，就生成反思、加入记忆，再重新执行。直到成功或到达预算。长期记忆并非无限保留：论文在部分任务中只使用最近三条反思，编程设置使用的容量又不同。

<a id="s4"></a>

## 4. 为什么摘要不等于反思

“我依次搜索抽屉、柜子、桌子，没有找到钥匙”是执行摘要，说明发生了什么。“没有检查门口挂钩，下一次应先检查未访问位置”才给出新的决策方向。

好的反思需要回答：哪一步造成失败，为什么原有判断不成立，下一次应修改什么。它应当比原轨迹更短，却保留改变行为所需的信息。若只是把轨迹换一种说法，记忆会变长，但下一次策略不一定改善。

<a id="s5"></a>

## 5. 不同任务怎样提供反馈

### 环境决策：识别无效循环

在 ALFWorld 中，Agent 通过文字动作操作环境。作者用规则或模型判断是否陷入重复：例如相同动作和相同响应连续出现，或者动作过多但没有完成目标。反思后重置环境再尝试。

### 知识问答：把答错转成检索或推理教训

在 HotpotQA 中，有的设置提供正确证据以隔离推理能力，有的需要 Agent 自行检索。反馈、可见证据和重试限制必须一起看，不能把这些设置混成一种“问答准确率”。

### 编程：自己生成测试，再分析失败

模型先生成代码和测试，在执行后根据错误修正。论文过滤语法无效的测试，并在相关设置中最多选择六条测试。最终评估仍使用基准的隐藏测试；内部自测和隐藏评估不是同一回事。[1，§4]

<a id="s6"></a>

## 6. 用分页读取程序走一遍

例如，任务要求读出某表全部记录。初次程序只执行一次查询，得到 25 条便返回。内部检查发现总数不符。

Evaluator 指出结果不完整。反思模块结合响应结构，发现存在续传标记，形成“HTTP 成功仅代表本页成功，应持续读取直到标记消失”的经验。第二次 Actor 修改循环，并继续检查是否处理空页、有标记但本页无记录等情况。

如果模型的自测只检查“至少返回一条”，错误就不会被发现。这说明反思效果的上限，取决于评价是否识别真正的失败。

<a id="s7"></a>

## 7. 反思记忆具体怎样进入下一次尝试

可以把同一个任务的运行过程写成下面的简化循环。记忆保存的是反思文本，当前尝试的动作轨迹则留给评价与下一次反思使用。[1，§3]

```python
reflections = []
for attempt in range(trial_budget):
    trajectory = actor(task, reflections, environment)
    feedback = evaluate(task, trajectory)
    if feedback.success:
        return trajectory
    lesson = reflect(task, trajectory, feedback)
    reflections = keep_recent(reflections + [lesson], memory_limit)
    environment = reset_for_retry()
```

实际任务中的环境和评价方式不同，这里只表示信息流。关键变化发生在第二次调用 Actor 时：它看见的任务可能没变，但多了“上次在哪一步走错、下一次怎样避开”的条件。没有这条回流路径，事后的反思写得再好也只是报告。

有限记忆容量使系统保留较近的修正，避免每次把全部失败轨迹重新读一遍。但这也可能淘汰一条后来仍有用的教训。原论文对同一任务内反复尝试的研究较多，不能把这种小缓冲直接当作大规模跨任务经验库。

<a id="s8"></a>

## 8. 把分页例子再往下走一步

第一版程序只读一页，反思指出要跟随续传标记。第二版加了循环，却写成“本页为空就退出”。如果接口允许空页仍带续传标记，程序还是会漏数据。

第二次失败提供了更细的反例。合适的反思应修正终止条件：“是否结束应依据续传标记，而非本页条数。”这比重复写“注意分页完整性”更有用，因为它直接改变代码中的判断。

| 阶段 | 可见证据 | 应产生的变化 |
| --- | --- | --- |
| 第一次失败 | 返回数量少，响应仍有标记 | 增加翻页循环 |
| 第二次失败 | 空页后仍有数据 | 修改循环终止条件 |
| 再次验证 | 所有页面覆盖且没有重复 | 才能确认该实现通过这些测试 |

这一过程中，反馈越能指出行为与目标的差距，反思越容易形成可执行的修改。只有一个“失败”标签时，模型得自己猜原因，错误归因的风险更高。

<a id="s9"></a>

## 9. 自生成测试为什么既有帮助，也会误导

编程任务里，测试让模型看见运行结果，而不只是检查代码表面是否合理。但测试本身由模型生成，可能与错误代码共享同一个误解。例如任务要求包含边界值，模型却在代码和测试里都把它排除了，内部验证就会通过。

另一种情况是测试要求超出题意，正确程序反而失败，模型为了迎合错误测试改坏代码。因此，内部测试成功只是当前验证集合下通过；论文最终仍用独立的隐藏测试计算表现。[1，§4.3]

HumanEval 的提升与 MBPP Python 的退步放在一起，说明这个方法的收益依赖反馈质量。对实际代码 Agent，我会保留现成测试、接口契约和运行环境提供的确定性信号，再让模型补充测试。反思可以解释反馈，却不宜同时垄断“出了什么错”和“现在已经正确”的判断。

<a id="s10"></a>

## 10. 实验结果既有提升，也有退步

论文在 ALFWorld 的 134 个任务中报告，带反思的 ReAct 通过多次尝试完成 130 个任务。这个数字体现的是带反馈的累计完成能力，不是一次尝试的成功数。[1，§4.1]

编程结果更能体现边界：

| 设置 | GPT-4 基线 | Reflexion | 解释 |
| --- | --- | --- | --- |
| HumanEval Python | 80.1% | 91.0% | 自测与反思有明显帮助 |
| HumanEval Rust | 60.0% | 68.0% | Rust 为文中选取并翻译的子集 |
| MBPP Python | 80.1% | 77.1% | 错误自测可能让修改更糟 |
| MBPP Rust | 70.9% | 75.4% | 收益依赖任务与测试质量 |

这些是论文报告的 pass@1 结果。其内部流程可以反复自测和修正，因此不能与不使用这些额外计算的单次生成简单视为同预算。[1，§4.3，Table 1–2]

作者分析 MBPP Python 的退步时，特别指出自生成测试产生假阳性的问题：错误程序通过内部测试，系统就过早认为成功。可见“能反思”并不保证反思方向正确。

<a id="s11"></a>

## 11. 局限在哪里

反思仍可能陷入局部错误认识；评价器若误判，会产生误导经验；有限缓冲区也不能自动支持跨大量任务的稳定积累。对于并发、外部 API、非确定行为等程序，可靠自测尤其困难。[1，§5]

另一个阅读要点是任务边界。原论文大量研究同一任务内的多次尝试，不能直接等价为一个跨数月、跨用户共享经验的长期平台。后者还要解决经验适用范围与失效问题。

## 项目实现与数据

> 实现与资源核查：2026-10-24。下面区分论文实验与后续项目演进；本节完成了资源与源码核查，未重新运行作者实验。

### 官方仓库按任务组织实验

论文旧链接中的作者账号已变更，可从 [noahshinn/reflexion](https://github.com/noahshinn/reflexion)访问代码。仓库把实验分为 `hotpotqa_runs`、`alfworld_runs` 和 `programming_runs`，分别对应问答推理、环境决策和代码生成，同时保存了实验日志。

先读 HotpotQA 部分容易看清机制：其 Notebook 提供无反思、只带上次尝试、只带反思、同时带两者等策略。区别不是更换一个“记忆数据库”，而是控制下一次回答能看见哪部分过去信息。[官方运行说明](https://github.com/noahshinn/reflexion/blob/main/README.md)列出了这些策略与 ALFWorld 的 `use_memory`、尝试轮数等配置。

### 一份日志应该怎样读

挑一个第一次失败、后来成功的任务，把任务输入、第一次轨迹、环境反馈、生成的反思与下一次轨迹并排看。假设第一次只搜索了物品名称，反馈显示位置不对，反思要求先检查所在房间；下一次是否真的先检查房间，才是值得观察的变化。这个例子说明阅读方法，不是原仓库中某条日志的转录。

仓库的 `root` 子目录保存不同实验的历史运行，编程部分还包含 HumanEval 等基准文件。原始题目、内部生成测试、最终评分测试承担不同职责：内部测试能指导修改，最终评分用于判断结果。把最终评分答案提前提供给反思模块，会改变原本的实验条件。

### 复现时记录重试预算

ALFWorld 需要对应环境，代码任务需要编译或执行环境，问答任务则需要正确的题目与检索设置。运行前先确定任务数、最多尝试几次、允许保存几条反思，再比较有无反思。否则“五次尝试后的最好结果”与“一次生成结果”混在一起，很容易把更多计算量算成记忆的全部贡献。旧日志可以帮助理解作者当时的行为；今天换模型重跑属于新的实验。

<a id="s12"></a>

## 12. 总结与看法

Reflexion 提供了一个清晰的无权重更新改进循环：尝试、评价、解释、保存、再尝试。它证明文字记忆可以成为行为改进的媒介，也展示评价质量会决定这种媒介是帮助还是误导。

这篇最有价值的地方，是把“错误信息”升级为“可复用的改进方向”。很多 Agent 不缺日志，缺的是从日志提炼下一次决策提示的机制。它的实现思想简单，因而适合成为经验学习的起点。

但我不会把模型自评当作真值。测试、环境反馈、事实校验能提供多少可靠约束，应先于反思文案的精美程度。MBPP 的反例比单个高分更值得重视：错误反馈经由流畅语言包装后，可能比原始错误更难察觉。

实际系统中，我会保存原始失败证据和反思的对应关系，统计这条经验后来是否真正奏效；对环境变化和反例允许撤回。这样错题本才会变好，而不是越记越自信。
