# Reflexion：Reflexion：通过语言反馈改进的语言智能体

**英文题名：** Reflexion: Language Agents with Verbal Reinforcement Learning

**版本与时间：** 2023  
**主题：** 经验改进  
**原文入口：** [主文](https://papers.nips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html) · [arXiv](https://arxiv.org/abs/2303.11366)  
**核对日期：** 2026-10-23  
**阅读依据：** [正文或技术版本](https://arxiv.org/html/2303.11366)；涉及补充稿的内容单独说明。本文为首版通俗解析，不包含独立实验复现。文中的教学例子与“本文推论”不是论文原始实验。

## 一句话理解

做错一道题后写下“下次先检查哪个条件”，再带着这条教训重做。模型不一定要重新训练，也可能通过外部记忆改善下一次决策。[1]

## 它针对什么问题

普通重试可能只是在重复采样：第一次做错了，第二次仍不知道错在哪里。Reflexion 希望把结果反馈加工成有用的经验，让重试带着方向。

## 三个角色怎样配合

**Actor** 负责执行任务；**Evaluator** 判断结果；**Self-reflection** 根据轨迹与反馈总结问题。总结写入情景记忆缓冲区，下一次尝试时作为上下文提供给 Actor。[1，§3]

反馈可以来自环境、规则或模型自身。这里的“语言强化”主要通过文字反馈影响后续行为，不等同于用梯度更新权重的传统强化学习。

## 教学例子：修复一个分页程序

第一次只拿到了第一页，测试提示数据条数不足。没有反思时，Agent 可能继续调整查询条件。有反思时，它记下：“接口成功不代表读取结束，应检查续传标记，直到没有下一页。”

这条教训比整段执行日志更便于复用，但必须与当时的接口和失败证据对应。这个例子不是论文实验。

## 实验怎么理解

论文在 ALFWorld、HotpotQA 和编程任务中研究反馈与反思的效果，并做消融分析。[1，§4] 阅读编程结果时，要一起看重试、测试反馈及计算预算，不能把经过反馈后的最终表现直接视为完全无反馈的一次生成能力。

## 局限与工程启示（本文推论）

错误归因可能出错：系统把网络故障总结成“这个 API 不可用”，就会形成有害经验。经验条目最好包含触发条件、失败证据、建议动作和不适用条件，并记录后来是否奏效。执行日志是证据，反思是待验证的提炼，两者都值得保留。

## 与其他论文的关系

与 MemoryBank 的用户事实记忆相比，它更关注失败教训；与 Voyager 相比，它主要保存语言经验，而 Voyager 的技能库保存可执行代码。
