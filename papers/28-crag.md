## 检索返回结果，不代表已经找到了答案

问“新版本是否支持某项接口”，检索返回三篇旧版本文档。它们与问题非常相似，却可能让模型得出错误结论。传统流程常把 top-k 直接送给生成器，而 CRAG 增加了一个判断：这批资料是否足够可信，还是需要换一种方式获取证据？

CRAG 的核心是检索后的纠正流程：评估候选，选择保留、补充或替换，再整理证据进入生成阶段。[1，§4]

这里的评估主要针对相关性。不要把论文里的 Correct 标签翻译成“已经确认每条事实真实且最新”。相关性判断与事实核验不是同一个任务。

<a id="s2"></a>

## 三条路径是怎样决定的

论文用微调后的 T5-large 作为 retrieval evaluator，逐一对“问题—段落”打分，再根据上下阈值决定整批结果的处理方式。[1，§4.2–§4.3]

| 判断 | 触发直觉 | 后续动作 |
| :--- | :--- | :--- |
| Correct | 至少有一份段落高于上阈值 | 对已有资料做知识精炼 |
| Incorrect | 所有段落都低于下阈值 | 放弃这批结果，获取外部搜索证据 |
| Ambiguous | 不属于上面两种情形 | 同时利用精炼后的已有资料与外部证据 |

中间状态很重要。若强制二选一，稍微错误的评分就会让系统全盘接受错误资料，或丢弃本来有用的证据。Ambiguous 给不确定情况保留补充信息的机会。

但“至少有一个高分”也不意味着多跳问题已经证据完整。业务若需要多个条件，应该进一步判断条件覆盖，而不能只复用单段相关阈值。

<a id="s3"></a>

## 知识精炼为什么先拆再合

一篇整体相关的文档，仍可能包含很多无关内容。CRAG 将文档分解为更细的 knowledge strips，检查这些片段是否有用，过滤后再组合成生成器使用的知识。[1，§4.4]

设资料包含三个部分：A 说明接口支持条件写入，B 讨论请求签名，C 说明某种条件表达式的限制。问题只问条件写入能力时，A、C 可能需要保留，B 可以去掉。这样减少噪声，也避免整篇长文占据上下文。

然而，拆分和过滤也会损失条件。若 A 写“支持该能力”，C 写“仅适用于某类资源”，只保留 A 就把有条件结论变成了无条件保证。因此精炼后的片段应能回到原始上下文；压缩得更短，不等于证据更完整。

<a id="s4"></a>

## 外部搜索在流程里承担什么角色

对于不可靠或不确定的检索，论文先改写查询，再通过 Web 搜索获得候选网页，选择并精炼其中内容，补充到已有知识之外。[1，§4.5]

这个选择针对的是静态语料覆盖不足的问题。它并不表示任何企业知识库都应该在失败时自动搜公网：内部项目、私有错误码和受限文档未必能在网上找到。工程上可以把替代证据源换成授权的其他索引、数据库或官方文档服务，但这是对 CRAG 思路的迁移。

因此，真正值得借鉴的是“识别检索失败并改变取证策略”，而不是必须使用某一家搜索 API。新的来源还需要可追溯，不能仅凭它来自另一个检索器就认为质量更高。

<a id="s5"></a>

## 一个完整例子

用户询问某接口的新版限制。第一次搜索只找到旧版说明，评价器给出中间分数，进入 Ambiguous。系统保留旧版中仍可能有用的基础定义，并改写查询加入接口名称和版本，查找新的发布说明。

如果新资料明确修改了限制，最终回答应说明版本差异，并把结论归因于新资料。若新资料也没有说明，合理结果可能是“当前证据不足”，而不是因为流程已经执行完就必须给确定答案。

这是教学演示。原论文的评价器并不天然具备完整版本语义；业务接入时仍要设计版本标签、过滤和冲突处理。

## 实验结果里也有不提升的情况

论文评测 PopQA、人物传记生成、PubHealth 和 ARC-Challenge，并区分生成模型配置。表 1 中，以 SelfRAG-LLaMA2-7b 为生成模型，标准 RAG 与 CRAG 在 PopQA 上分别为 52.8 和 59.8，提升 7.0 个百分点。[1，表 1]

同表里 Self-RAG 与 Self-CRAG 在 ARC 上分别为 67.3 和 67.2，并没有提升。这很有价值：纠正流程能改善多项结果，但不代表每个任务都受益。

表 2、表 3 分别去掉路径和精炼、查询改写、来源选择等环节，帮助判断各组件的作用。读结果时还要考虑额外 Web 访问带来的信息增量与成本：一个能查更多来源的系统，与固定 corpus 系统的比较，不能简单解释为相同证据下的算法优势。

<a id="s7"></a>

## 项目实现与数据

[HuskyInSalt/CRAG](https://github.com/HuskyInSalt/CRAG) 提供预处理、相关性评估、知识精炼、搜索与生成的流程说明。官方步骤分别产生 correct、incorrect、ambiguous 对应的材料，再供后续生成使用。[2]

数据包括 PopQA、PubHealth、ARC-Challenge 和传记相关任务；论文复用了 Self-RAG 的部分初始检索结果，使初始候选更容易对齐。评价器训练则需要“问题—段落”相关性信号，不能仅准备最终答案。

读实现时，应跟踪一条 query 在各中间文件里的身份和分数，检查替换路径是否仍错误保留被判为无关的段落。复现 Web 搜索还受到网页变化影响，最好保存当次网页内容和访问日期。本篇没有调用搜索生成完整实验结果。

<a id="s8"></a>

## 总结与看法

CRAG 将检索失败变成一个可处理的状态，而不把所有问题推给生成器。对工程而言，这通常比单纯增加 top-k 更值得尝试，因为它要求系统辨别“证据还不够”和“可以开始回答”。

我会保留三态判断与精炼思路，但按业务定义补救来源，并测量评价器误判造成的代价。若错误判断让系统丢掉唯一正确证据，多一个控制模块反而可能变差。是否采用，应看真实失败样本中的修复率、误伤率和额外成本。
