## 检索成功之后，问题还没有结束

用户问一项故障修复为什么有效。段落 A 描述原来的故障条件，B 描述代码修改，C 给出修复后的验证结果。检索器把三段都找到了，但只阅读其中一段，答案仍可能缺少关键环节。

FiD，即 Fusion-in-Decoder，把注意力放在“多段资料怎样被生成器共同利用”上。它先独立编码各段，再让一个解码器综合所有编码结果生成答案。[1，§3] 上面的故障案例只是帮助理解融合需求，并非论文原始实验。

这个设计看起来简单，却改变了多文档处理的计算方式。把所有段落直接拼成长序列，会让编码器在整个长序列上进行自注意力；FiD 把跨段落的信息融合推迟到解码阶段。

<a id="s2"></a>

## 为什么每段都要附上问题

对检索得到的每个 passage，FiD 构造“问题＋标题＋段落”的输入，分别交给共享参数的编码器。每段得到一组隐藏表示，随后沿序列维度连接，供同一个解码器的 cross-attention 访问。

这些并非互不相关的模型副本，而是同一个编码器分别处理不同输入。把问题重复放入每段，可以让编码结果从一开始就考虑当前问题，而不只是保存一份通用文档表示。

这里还要区分两种向量：DPR 的段落向量用于从海量文档中找候选；FiD 编码器的隐藏表示用于阅读已经选出来的候选。后者通常随问题变化，不能把它直接当成可长期复用的 ANN 索引向量。

<a id="s3"></a>

## “在解码器融合”到底发生在哪里

假设检索出 N 段，每段编码为 L 个 token 的表示。编码器分别处理 N 个长度为 L 的输入，解码器看到的则是合在一起的 N×L 个表示。

生成“修复有效，是因为……”时，解码器可以在同一步对故障条件、修改说明和验证结果分配不同注意力。它没有被限制为只选择某一份段落生成整个答案。[1，图 2]

从注意力计算直觉看，直接拼接时，编码器自注意力涉及约 $(NL)^2$ 个位置对；独立编码大约涉及 $NL^2$ 个位置对。这只是在解释编码器自注意力部分，不是整套系统的精确复杂度。解码器仍需要访问全部编码表示，显存、编码次数和生成成本都不会消失。

这也是 FiD 与原始 RAG 的关键差异：RAG 对每个文档条件下的生成概率进行混合；FiD 先把多份文档的隐藏表示提供给同一个解码器，由它进行联合阅读。

<a id="s4"></a>

## 一个具体的阅读过程

继续用故障案例。问题是“为什么这次修改能避免重复消费？”

| 编码输入 | 资料内容 | 对回答的作用 |
| :--- | :--- | :--- |
| 问题＋A | 重连后从初始位置重新读取 | 解释旧行为为什么会重复 |
| 问题＋B | 保存最近成功处理的序列号 | 解释新增状态 |
| 问题＋C | 恢复时使用该序列号定位 | 解释状态怎样参与恢复 |

读完三段，合理答案应把因果链连接起来，而不只是重复三句原文。如果 B 保存的是“最近读取”而非“最近成功处理”，结论可能改变。这提醒我们，融合能力必须保留条件，不能只拼接听起来连贯的说法。

FiD 的架构允许多段共同参与，但并没有提供一个能自动证明因果正确的符号系统。最终是否读懂，仍要由模型训练与评测决定。

<a id="s5"></a>

## 实验为何值得看

论文用 T5 初始化模型，在 Natural Questions、TriviaQA 和 SQuAD Open 上比较结果。NQ、TriviaQA 使用 DPR 检索，SQuAD 使用 BM25；主要配置在训练和推理时使用 100 个 passage。[1，§4]

表 1 中，FiD-large 的 NQ Exact Match 为 51.4，TriviaQA 的开放域测试列为 67.6。表格另列了另一种 TriviaQA 评测设置，因此不能随意拿不同列比较。Exact Match 也不是要求逐字节一致，而是按评测规则归一化后匹配可接受答案。

更值得关注的是控制变量实验：论文增加 passage 数量，观察 reader 是否能把更多证据转化为更高准确率，也比较训练时使用不同 passage 数量的影响。[1，图 3、表 2]

这些结果说明当时的模型在该设置下可以从更多段落获益，不支持“top-k 越大永远越好”。增加候选同时带来更多噪声、更高显存和更长延迟。将 FiD 结论迁移到今天的聊天模型时，需要重新测量，而不是直接把 top-k 设成 100。

<a id="s6"></a>

## 项目实现与数据

[facebookresearch/FiD](https://github.com/facebookresearch/FiD) 提供模型、训练与评估入口。原始 FiD reader 主要看 `train_reader.py`、`test_reader.py`，数据下载从 `get-data.sh` 进入。[2]

输入数据包含问题、答案列表以及检索上下文 `ctxs`；各上下文包括标题和文本。首先检查数据加载器如何截断每个 passage，再看模型如何把 batch 与 passage 维度合并编码，最后看 decoder 如何接收拼接后的隐藏状态。沿这个顺序读代码，比先研究分布式训练参数更容易对应论文。

官方仓库还包含从 reader 的注意力信号训练 retriever 等后续工作。不能因为代码在同一个仓库，就把所有功能都归入这篇 EACL 2021 论文。

复现时尤其要固定文档检索结果。如果同时换 retriever、候选数量和 reader，就无法判断收益来自哪里。一个有用的小实验是固定 100 个候选，再分别使用前 5、20、50、100 个测量答案质量和成本。本篇提出这种验证思路，没有运行实验。

<a id="s7"></a>

## 总结与看法

FiD 让“找到资料”和“读懂资料”之间的区别变得很具体。检索器只保证材料有机会进入系统，reader 还要在有限资源下整合信息、忽略噪声并保留条件。

我更看重它推迟跨文档交互的设计思路：哪些计算可以独立完成，哪些阶段真正需要共同访问全部证据？这个问题对系统分层很有启发。但若业务只是从单份文档查一个字段，复杂的融合未必值得；若任务需要综合多份资料，FiD 则提供了清楚的研究起点。
