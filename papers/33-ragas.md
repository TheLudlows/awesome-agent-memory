## 评价一个回答，需要先问“好”指什么

用户问“怎样从断点恢复”，系统准确复述了一段鉴权说明。这段话可能完全忠于来源，却没有回答问题。另一种情况是，回答正确提到保存序列号，但证据从未说明这一点，模型是靠已有知识补出来的。

只打一个总体分数，很难区分这些情况。原始 RAGAs 论文提出三类无需人工参考答案的评价：faithfulness、answer relevance 和 context relevance，分别检查回答是否有据、是否切题，以及上下文是否包含过多无关材料。[1，§3]

“无需参考答案”不等于“无需输入资料”。仍然需要问题、检索上下文和生成答案；评判还依赖语言模型及部分 embedding 计算。

<a id="s2"></a>

## Faithfulness：回答中的说法受到支持吗

方法先把回答拆成较短陈述，再让评判模型判断每条陈述能否从给定上下文推得。得分为受支持陈述占全部陈述的比例：

$$
F=\frac{\text{受上下文支持的陈述数}}{\text{回答中的陈述总数}}
$$

例如回答包含“需要保存序列号”“恢复时使用该序列号”“任何情况下都不会重复”三条说法，证据只支持前两条，教学算例中的 faithfulness 为 2/3。[1，§3]

这个指标测的是相对于上下文的忠实性。若上下文本身过期，忠实复述也可能答错现实问题；若回答只写一句有据但不完整的话，faithfulness 仍可能很高。因此它必须与其他维度配合。

<a id="s3"></a>

## Answer relevance：从答案反推问题

原论文让模型根据生成答案提出若干可能的问题，再比较这些问题与原问题的 embedding 余弦相似度，取平均作为回答相关性信号。[1，§3]

直觉是：若答案真正回应“如何恢复消费”，由它反推出来的问题也应该围绕恢复消费；如果反推结果主要是“如何配置鉴权”，说明答案可能偏题。

这种方法避免只凭一个笼统评分指令判断，但它仍是代理指标。两个语义接近的问题可能要求相反答案，例如“哪些版本支持”和“哪些版本不支持”。高相似度不能证明逻辑正确，也不能单独证明事实完整。

<a id="s4"></a>

## Context relevance：材料里有多少真正有用

原论文让模型从检索上下文中提取对回答问题有帮助的句子，再用相关句子数除以上下文总句子数。[1，§3]

这个定义反映上下文的集中程度，能惩罚塞入大量无关材料。但它并不等于召回率：如果系统只找回一条关键事实、漏掉另外两条，剩下的上下文仍可能非常“纯”。

句子切分方式也会影响计数。某些长句同时包含多个事实，有些列表项很短，不能把一个比例当成绝对不受格式影响的客观测量。

<a id="s5"></a>

## 三项指标怎样一起看

以下是诊断思路，不是论文实验结果：

| 现象 | 可能原因 | 下一步检查 |
| :--- | :--- | :--- |
| 忠实但不切题 | 引用正确资料，却回答了旁支问题 | 检索目标、提示与答案内容 |
| 切题但缺乏支持 | 模型靠参数知识补充，或添加过强结论 | 逐条陈述与原始证据 |
| 上下文很杂 | 候选包含大量无用信息 | 重排、去重和片段边界 |
| 三项都不错但答案缺内容 | 没有参考答案，遗漏不容易被发现 | 人工完整性检查或补充标注 |

最后一种情况很重要。没有标准答案时，自动指标对“根本没提到的事实”可能不敏感。对于有明确必答条件的业务，应单独列出这些条件，而不是让参考自由评价承担所有责任。

<a id="s6"></a>

## 论文怎样验证这些评价

作者构建 WikiEval，从 Wikipedia 内容生成问题与回答，并请人工对相关维度进行判断，再考察自动评价与人工判断的符合情况。[1，§4–§5]

这属于“评价指标本身的评价”。一个指标能稳定输出数字还不够，它应在合理程度上接近人对同一维度的判断。原论文的英文、有限规模数据支持的是初步有效性，不能直接证明它在中文数据库文档、代码片段和多轮运维任务中同样可靠。

模型裁判还会受到提示、模型版本和资料长度影响。更换裁判模型后，分数变化可能来自评价器，而不是被测 RAG 系统。做版本对比时，应固定评价配置并保留原始判断。

<a id="s7"></a>

## 项目实现与数据

[Ragas 官方文档](https://docs.ragas.io/) 提供安装、RAG 评价、指标和数据使用说明，当前文档链接到 [vibrantlabsai/ragas](https://github.com/vibrantlabsai/ragas)。项目已扩展出更多评价能力，不能把今天全部 API 和指标归为原始论文贡献。[2]

尤其需要区分：原论文重点讨论 reference-free 的三个维度；当前工具的一些指标可能需要参考答案或其他字段。采用前应检查具体指标的输入要求，而不是看到“Ragas”就认定一定不需要标注。

数据准备可从每次请求保存的 question、retrieved contexts 和 response 开始。为抽样人工核验，还应保存文档 ID、来源版本和模型配置。WikiEval 的数据说明见论文；当前工具的测试集生成流程属于另一个需要单独理解的部分。

我建议先取几十条真实业务样本，对每条自动判断人工复核，检查是否反复漏掉否定、版本和条件。之后再扩大自动评测规模。本篇没有调用评价模型，也没有生成业务分数。

<a id="s8"></a>

## 总结与看法

RAGAs 降低了建立第一版评价流程的门槛，也让“有据、切题、材料集中”成为可以分别讨论的问题。它适合在标注不足时帮助发现问题和观察趋势。

我不会把一个高分当成系统可以上线的充分条件。评价器需要校准，来源需要可信，完整性需要额外检查。自动指标最有价值的用途，是把值得检查的样本暴露出来，并在固定口径下追踪变化。
