## 为什么一个榜单分数不够

一个模型擅长检索百科答案，不一定擅长找医学证据、金融讨论或反驳某个观点的文章。不同领域的词汇不同，更重要的是，“相关”的含义也不同。

问题重复检测希望找到意思相同的问题；论点检索可能希望找到回应或反驳；事实核验需要能支持或质疑某个说法的证据。简单的主题接近未必足够。

BEIR 整理了多种任务和领域，评估模型在没有针对目标任务重新训练的情况下是否仍然有效。原论文覆盖 18 个英文数据集、9 类检索任务。[1，§3] 它评测的是检索，不直接评价生成答案。

<a id="s2"></a>

## Zero-shot 在这里是什么意思

零样本通常指模型没有使用目标评测数据进行监督适配，不代表模型没有训练过。一个检索器可以先在 MS MARCO 上训练，再去其他领域评估泛化能力。

这个区别很关键。如果用目标测试集反复选择模型、阈值和提示，再把结果称作完全未知领域泛化，评价就已经掺入了目标信息。应保留独立验证集或明确说明选择过程。

论文比较词面、稀疏、稠密、后期交互及重排方法，观察不同架构在领域变化下的表现与计算代价。[1，§4–§5] 这些是当时的模型比较，不是所有后续 embedding 模型的固定排名。

<a id="s3"></a>

## 数据格式如何把检索任务统一起来

BEIR 把任务整理为三个核心部分：[2]

| 文件或对象 | 内容 | 对应系统中的角色 |
| :--- | :--- | :--- |
| corpus | 文档 ID、标题、正文等 | 待建立索引的资料 |
| queries | 查询 ID、查询文本 | 请求集合 |
| qrels | 查询与文档之间的相关性标注 | 用于评价排序的参考 |

这种统一方式让同一检索接口可以跑多个集合。生成答案不是必要步骤，只需对每个 query 输出文档 ID 和分数。

标题是否拼入正文、长文怎样截断、同一文档是否切成多块，都会改变结果。若引擎只返回 chunk ID，还需要明确映射回文档 ID 的规则，不能把一个文档的多个 chunk 当作多个独立相关文档重复计分。

<a id="s4"></a>

## nDCG、Recall 和 MRR 关注不同问题

Recall@k 看标注相关文档中有多少出现在前 k 个结果。MRR 关注第一个相关结果的位置。nDCG 则考虑相关性等级与排列顺序，对越靠后的收益进行折扣，再与理想排序归一化。

例如有三份已标注相关文档。系统 A 把其中一份排在第一，但漏掉其余两份；系统 B 把三份都放进前十，却第一份在第五位。A 的 MRR 更好，B 的 Recall@10 更好。用户要一个直接答案还是要完整调查材料，会影响更看重哪个指标。

BEIR 主要使用 nDCG@10 等指标比较检索效果。[1，§4] 但工程选择还要加入 P95 延迟、内存、索引构建和更新成本。这些不能从一个相关性分数推算出来。

<a id="s5"></a>

## 标注没写相关，真的就是不相关吗

大型语料无法对每个查询的全部文档逐一标注。评测往往先用一些系统取候选，再人工判断。若候选主要来自词面检索，稠密检索独有的相关文档可能没有进入标注池。

论文专门讨论这种 lexical bias，并在 TREC-COVID 上补充相关性判断，观察不同方法的分数变化。[1，§6] 这提醒我们：评测分数反映“相对于已有标注的表现”，标注本身也有覆盖边界。

不能因此忽视指标，但遇到一个新系统明显找出合理结果、分数却下降时，值得人工复查未标注文档。尤其是业务数据自建 qrels 时，应从多种检索方法汇总候选，减少单一路线偏差。

<a id="s6"></a>

## 实验最值得带走的结论

原论文发现，没有一种方法在所有集合上稳定胜出，域内成绩与域外表现也不总一致。BM25 在若干零样本任务中仍是强基线，后期交互和重排方法往往有质量优势，同时需要更高计算成本。[1，§5]

这不是“BM25 永远优于向量检索”，而是要求我们停止只看单个训练域的排名。模型选择应该结合自己的语料与任务。对于数据库文档，错误码、版本号、接口名等精确词可能很重要；概念性排障问题又可能需要语义召回，两类请求应分别测量。

跨数据集均值也可能掩盖严重退步。如果某系统在多数小任务略有提升，却在核心业务任务大幅下降，平均分更高未必值得采用。

<a id="s7"></a>

## 项目实现与数据

[beir-cellar/beir](https://github.com/beir-cellar/beir) 提供 `GenericDataLoader`、检索模型适配与评价流程，数据可从 [BeIR 的 Hugging Face 页面](https://huggingface.co/BeIR) 或官方清单进入。[2]

原论文的数据集数量与当前软件可直接下载的集合数量不必相同。部分集合受原始数据许可或分发方式影响，需要按说明获取；不能把框架开放源代码理解成全部数据都可任意使用。

若要比较自己的搜索引擎，可以先用较小集合验证 corpus、query、qrels 的映射，再扩大规模。保持同一文档处理方式、同一硬件、同一索引参数目标，分别测量质量与性能。本篇没有运行 benchmark，也没有对任何业务引擎给出实测结论。

<a id="s8"></a>

## 总结与看法

BEIR 的贡献主要在评价方法：让检索模型走出熟悉的数据集，面对不同含义的“相关”。它促使我们把泛化能力当作需要检验的属性，而不是从模型规模或一个榜单推断出来。

对于检索底座，我会保留公开集合来观察一般能力，同时建设覆盖精确查询、概念查询和多条件查询的业务集。公开 benchmark 负责提供共同参照，业务数据负责判断实际收益，两者缺一不可。
