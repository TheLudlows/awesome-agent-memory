## 1. 为什么越总结，经验反而越少

设想一个操作数据库 API 的 Agent，第一次只读取第一页数据，遗漏了后面的结果。任务结束后，它留下经验：“当响应仍然携带分页游标时，应继续读取，不能只根据本页条数判断结束。”

这是一条有具体判定条件的经验。后来加入更多教训，系统不断要求模型“把所有旧经验和新经验重新整理得简洁一点”。原先这句话可能逐渐缩成“注意分页”，再缩成“正确调用 API”。表达越来越整齐，真正能阻止错误的信息却消失了。

ACE 研究两种相关问题：偏好过度简短的通用指令，导致领域细节被抹去；反复整体重写上下文，导致已有信息逐渐坍缩。[1，§2] 论文中的 context collapse 指这种上下文内容退化，不是模型权重崩溃，也不是服务超出窗口后直接报错。

上面的 API 场景是本篇教学例子。它说明，记忆的价值常常存在于条件和例外里，而不是存在于一句听起来正确的口号里。

## 2. Playbook 保存的究竟是什么

ACE 将上下文视为持续演进的 playbook，可以理解为做任务时随身查阅的经验手册。里面包含策略、领域知识和常见错误，不必只是用户事实或聊天摘要。[1，§3]

论文把内容组织成结构化条目，条目带有标识及 helpful、harmful 等反馈计数。作者实现中也可以看到按栏目和 ID 组织的文本格式。下面是自拟示例，不是作者的数据：

```text
## API 调用
[api-00001] helpful=3 harmful=0 ::
分页结束条件应以目标 API 的游标协议为准；本页为空时也要检查是否仍有后续游标。
```

这里有三类信息。正文描述可复用经验；ID 用于指出哪一条被使用或需要修订；计数记录先前反馈。它们使系统能对局部条目操作，而不是每次处理整本手册。

不过，`helpful=3` 不等于“正确概率为 75%”，也不表示经过三次严格因果验证。它只是被相应流程标记有帮助的次数。一个常被使用的错误建议，也可能因为反馈不可靠而积累高分。

因此我会把适用条件、来源和失败反例作为业务扩展重点。论文的基础条目机制为这些能力提供了位置，但不能从几个计数器推导出一个完整的知识可信度系统。

## 3. Generator、Reflector、Curator 怎样分工

ACE 将执行任务、分析经历和整理经验拆成三个职责。[1，§3]

| 角色 | 输入与工作 | 输出 |
| :--- | :--- | :--- |
| Generator | 使用当前任务与 playbook 产生回答或行动 | 任务轨迹、结果，以及条目使用反馈 |
| Reflector | 检查轨迹与结果，分析有效做法和失败原因 | 对这次经历的经验判断 |
| Curator | 将经验判断与已有条目对照，整理局部改动 | 可并入 playbook 的增量内容 |

它们是三个功能角色，不要求三个不同型号的模型，也不要求三个常驻服务。论文实验使用相同的 DeepSeek-V3.1 非思考模式承担这些角色，避免把更强反思模型带来的能力直接当成上下文方法的收益。

为什么不能让执行者顺手写一句总结？可以这样做，但执行者容易把自己的假设当成已经得到验证的原因。单独检查轨迹，至少让“任务做得怎样”和“应该学到什么”成为两个明确步骤。

当然，职责分开不等于错误自动消失。Reflector 可能错判原因，Curator 也可能把只适用于一个环境的经验写成通用规则。三个角色只是让错误发生的位置更可观察，并没有替代可靠的环境反馈。

## 4. 增量更新如何保住已有经验

ACE 的核心选择是产生小规模 delta，而不是让 LLM 每次重新生成全部上下文。Curator 提出的局部内容由程序合并到现有状态，已有条目不必在每次更新时都重新经过一次语言压缩。[1，§3.1]

例如，原手册已经有连接超时、认证和分页三类经验。新任务只发现分页游标的一个边界条件，更新就应该集中在分页条目。认证部分没有新证据，不需要为了一次总结把它重新改写。

这里可以借用补丁的直觉：审查一个小改动，通常比比较两份完整重写后的文档更容易发现遗漏。这个直觉来自工程经验，不代表 ACE 已经提供了数据库级事务或版本控制。

一套可检查的业务实现可以记录：修改前版本、使用的轨迹、提出的 delta、应用后的版本。这是本文建议。这样任务质量下降时，可以判断是某条经验新增后造成误导，还是原有条目被整理过程误删。

并行产生多个 delta 时也存在冲突。不同执行者可能从不同任务里总结出相反策略。确定性的合并程序能够保证相同输入得到相同输出，却不能保证两条语义上矛盾的经验已经被正确解决。

<a id="s5"></a>

## 5. 经验越来越多以后怎样整理

只追加能避免一次重写丢掉全部细节，却会产生另一个问题：重复、过时和不适用的经验不断堆积。ACE 因而提出 grow-and-refine：允许增长，再通过计数更新、去重等整理控制冗余。[1，§3.2]

论文讨论使用语义 embedding 比较条目，并可选择主动整理或到达上下文限制后再整理。主动整理把成本分摊到每次更新；延迟整理减少频繁维护，却可能在某次请求前付出集中成本。

语义相似不等于可以合并。下面两条经验用词相近，但范围不同：

- API A 中，本页为空但仍有游标，应继续读。
- API B 中，只有确认游标缺失才算结束。

若两个接口的协议不同，合并成“空页继续读”就可能丢掉必要限制。因此去重应该检查对象和条件，而不是只删除相似度高的句子。

还有一个阅读边界：论文将细粒度条目视为支持检索与局部使用的基础，但不能据此声称作者已验证了任意规模的条目检索系统。给模型更长手册，也不保证它能始终选择正确经验；仍需要测量使用率、干扰和上下文成本。

## 6. 用一条分页经验说明学习过程

以下是把 ACE 思路用于 API Agent 的教学推演，不是论文 AppWorld 的实验记录。

Agent 第一次调用列表接口，拿到 100 条后结束；验证发现共有 230 条，轨迹里明明有 next token。日志只记录“漏读了 130 条”，Reflector 则要提出原因：“错误地把一页结果当成完整结果”。这还只是解释，下一步要变成能改变行为的条目。

| 对象 | 示例内容 | 下次能起什么作用 |
| :--- | :--- | :--- |
| 执行轨迹 | 请求返回 100 条及 next token，随后结束 | 保留判断依据 |
| 反思 | 因未继续使用游标而遗漏后续页面 | 提出失败原因 |
| Playbook 条目 | 对接口 X，持续读取返回游标，直到响应不含游标；不要以页长判定结束 | 提供明确的执行与停止条件 |

假设已有条目 P1 说明鉴权、P2 说明重试，新经验成为 P3。增量更新只添加 P3，P1 和 P2 不必重新经过模型总结。普通整段重写则可能在加入 P3 时，把 P2 的具体重试条件缩成“失败后重试”。ACE 要避免的损失发生在这里：新知识写进去了，旧知识的关键条件却悄悄消失。

下一次列表任务使用 P3 连续取完三页，可以给它有帮助的反馈。随后另一种接口的游标过期，重用旧游标失败，则需要区分接口和失败条件，不能把 P3 推广成“所有列表都照这样重试”。有帮助的次数是使用反馈，不是这条规则普遍成立的证明。

论文讨论局部更新与整理，但本篇核查的代码提交仍对支持的操作有限制，详见实现节。这里的反例修订是设计上应该检查的行为，不能据此认定发布代码已完整支持 UPDATE、MERGE、DELETE。

我会用一个很具体的回归检查评价这种机制：新增 P3 之后，P1/P2 的关键条件是否保留，下一任务是否实际遵守 P3。手册变长和条目数量增加都不能替代这两项观察。

## 7. 离线学习与在线适应有什么区别

ACE 的学习主要改变输入上下文，基础模型权重保持不变。论文支持两种实验方式。[1，§4.1]

离线方式在训练任务上形成经验手册，再到测试任务上评估。这里可以反复处理训练样本，但必须区分训练、验证和测试，不能一边看测试答案一边声称测量的是未见任务上的固定能力。

在线方式按顺序处理测试样本：先用当前手册回答，再利用该样本反馈更新手册，使后续样本受益。这种设置测量的是连续适应能力，题目顺序和可见反馈都会影响结果。

| 需要明确的条件 | 为什么影响结论 |
| :--- | :--- |
| 是否提供标准答案 | 决定反思能否直接知道结果对错 |
| 是否只有执行反馈 | 代码成功执行不等于业务目标成功 |
| 样本顺序与重复次数 | 早期经验会影响后续任务 |
| 测试前是否已有手册 | 决定起点是空状态还是已积累经验 |

论文展示无标准答案条件下仍可利用执行反馈，但这不能改写成“不需要监督信号”。错误码、环境状态和任务结果本身都在提供信息。如果环境几乎不给可靠反馈，经验更新会更难。

## 8. 实验、消融与成本

论文在 AppWorld 以及金融领域的 FiNER、Formula 上评估 ACE。AppWorld 涉及工具与 API 交互；FiNER 涉及财务文本细粒度实体标注，Formula 涉及结构化财务数据计算，不能笼统当作同一类问答。[1，§4]

下面摘取 v1 表 1 的离线设置，展示“是否给标准答案”的区别。基础模型均为 DeepSeek-V3.1，数值为作者报告：

| 方法 | 适应时提供标准答案 | Test-Normal TGC | Test-Challenge TGC |
| :--- | :---: | ---: | ---: |
| ReAct 基线 | 不适用 | 63.7 | 41.5 |
| ReAct + ACE | 是 | 76.2 | 57.3 |
| ReAct + ACE | 否 | 75.0 | 54.4 |

TGC 是任务目标完成指标，论文另报 SGC。不能把这两列解释成检索召回率，也不能把不同指标的均值当作“所有任务中统一比例的成功率”。无标准答案仍有提升，支持执行反馈可以帮助形成经验；有标准答案表现更好，也说明反馈质量重要。

作者通过移除反思等组件和调整适应过程做消融，讨论分工与多轮改进的作用。但这不保证每个业务都需要相同角色数量、相同轮数。实际系统应该检查改动是否带来可复现收益，而不是为了符合图示增加调用。

成本部分讨论的是适应过程的延迟、rollout 和 token 费用。例如，离线 AppWorld 与 GEPA 的比较、在线 FiNER 与 Dynamic Cheatsheet 的比较，处于不同实验场景。不能把汇总的适应延迟下降数字解释成“每次用户请求都快同样比例”。[1，§4.6]

长手册会增加输入，但更好的策略也可能减少工具误用和反复尝试。最终划不划算，需要一起统计手册读取、任务执行、反思、整理和失败重试，而不是只数 prompt 长度。

| [`ace/core/reflector.py`](https://github.com/ace-agent/ace/blob/82709de050e1db6e6ef2f07bcb0393560b94992a/ace/core/reflector.py) | 轨迹与反馈如何形成经验 |
| [`ace/core/curator.py`](https://github.com/ace-agent/ace/blob/82709de050e1db6e6ef2f07bcb0393560b94992a/ace/core/curator.py) | 模型提出的操作怎样解析、检查并应用 |
| [`eval/finance`](https://github.com/ace-agent/ace/tree/82709de050e1db6e6ef2f07bcb0393560b94992a/eval/finance) | 数据处理与离线、在线评估入口 |
| [ACE AppWorld](https://github.com/ace-agent/ace-appworld) | 独立的任务环境、配置和实验步骤 |

源码有一个不能略过的细节：Curator 的说明列举 ADD、UPDATE、MERGE、DELETE，但当前验证逻辑明确注明只有 ADD 得到完整支持；批量提案路径还会筛选 ADD 操作。因而不能仅凭文件顶部注释，声称完整的增删改合并都已实现。论文的 grow-and-refine 思路与某个代码版本的能力，需要分别理解。

官方 README 还列出条目使用日志、Curator 操作差异、阶段性 playbook 和最终评估结果。这些产物很有价值：它们允许把任务效果与具体经验改动对应起来。复现时应保留模型、反馈设置、任务顺序、反思次数和手册预算，不能只保存最后一个分数。

AppWorld 仓库说明需要从其源码安装定制环境，再下载数据；它不是简单安装同名 PyPI 包就能完整复现。FiNER 和 Formula 则走金融数据处理与评估入口。两种实验所依赖的环境、数据和成功判定不同。

本篇核查了上述资源与部分实现，没有执行作者实验。工程接入时也应先确认代码实际支持的操作，再决定如何维护删除、冲突修订和持久版本。

## 10. 总结与看法

ACE 值得选读的地方是更新方式：把经验拆成可以标识和局部合并的条目，减少整段重写时丢失细节的机会。这是上下文维护上的具体改进，基础模型并没有因此更新权重。

反思与整理分工让错误比较容易定位，但角色数量本身不是主要贡献。Reflector 若从一次偶然成功总结出错误规律，Curator 即使无损保存，仍是在积累错误。因此，条目化解决的是表达与维护问题，经验是否成立仍取决于反馈和后续检验。

AppWorld 的有标准答案与无标准答案对照，都显示这套流程有帮助；后者仍然利用环境反馈，不能说完全没有监督。适应过程成本与日常任务成本也不同，不能把适应阶段更快直接解释为每次用户请求更快。

对经常重复相似工具任务的 Agent，我会优先尝试保留条件和例外的局部经验更新，并检查旧经验有没有因新增内容而退化。是否需要完整的三角色、多轮整理流程，应由任务收益决定。代码实际能执行哪些编辑操作，也必须与论文的设计空间分开看。
