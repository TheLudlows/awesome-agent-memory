## 1. 为什么保存执行轨迹还不等于学会经验

一个网页任务可能记录几十次点击，代码修复可能留下几百行命令输出。这些轨迹完整，却夹杂大量偶然细节。下一次问题不同，直接取回旧轨迹可能只让模型模仿旧路径，而不是理解应该遵循的判断原则。

ReasoningBank 希望把经历提炼成可迁移的推理策略，而且同时利用成功与失败。它研究的是测试时不断积累的外部经验，不要求在每个任务后更新基础模型权重。[1，§3]

<a id="s2"></a>

## 2. 记忆条目为什么只分标题、描述和内容

**标题**概括策略；**描述**用一句话说明用途；**内容**记录推理步骤、决策理由或操作认识。形式简洁，便于人理解，也便于检索后放入 Agent 指令。

例如，一次失败日志是“多次点击提交按钮后发现状态没有变化”。更可迁移的条目可以是：“提交后先检查状态变化；如果页面没有反馈，不要连续重复同一操作，应确认是否存在验证错误或异步处理。”

后者剥离了某个按钮的位置，却保留改变行为的判断规则。抽象得太少会局限于原页面；抽象得太多则只剩“操作前要谨慎”这种没有用的空话。[1，§3.2]

<a id="s3"></a>

## 3. 一次任务怎样进入长期经验循环

### 先检索可用经验

系统以当前问题与上下文检索 top-k 相关条目，把内容作为额外指令提供给执行 Agent。记忆影响后续行动，而不仅在任务结束后生成一份报告。

### 再判断当前轨迹的结果

任务结束后，LLM 裁判根据任务与轨迹给出成功或失败的代理判断。论文设定中，这一步不读取测试时的标准答案，因此是自评信号，不是真实结果的绝对保证。

### 最后构造并纳入新条目

成功经历提供可复用策略，失败经历提供陷阱与反事实改进方向。在本文依据的 v1 中，consolidation 刻意采用简单加入，以突出经验表示本身的作用，不应把它描述成已经实现复杂去重与冲突消解的记忆治理系统。[1，§3.2]

<a id="s4"></a>

## 4. 为什么失败经历也有价值

成功轨迹只告诉你某条路走通了，失败可能告诉你哪些前提不存在、哪些捷径不成立。例如“看到名称相似就认为是同一文件”导致修改错误对象，这条教训可以迁移到许多软件任务。

但失败经验不能直接写成一条普遍禁令。某次接口超时不等于该接口永远不可用；某种搜索没有找到结果，也不证明资料不存在。提炼应保留条件，而不是把一次失败扩大成所有场景的规律。

这是理解 ReasoningBank 的关键：它要提炼策略，不是把模型刚刚的情绪化解释永久保存。

<a id="s5"></a>

## 5. MaTTS：怎样把额外尝试变成更好的记忆

普通测试时扩展会增加尝试次数，再选择更好的输出。ReasoningBank 进一步问：这些额外经历是否也能变成以后受益的经验？MaTTS 提出并行与顺序两种方式。[1，§3.3]

### 并行方式

同一道任务生成多条轨迹，对比成功与失败，识别稳定的有效策略和偶然路径。多个尝试提供对照，理论上比单次自评更容易过滤看似合理却不可靠的经验。

### 顺序方式

在一条任务过程中继续修正与反思，不只保留最终答案，也从中间纠错记录提取经验。中间的“为什么改了方向”可能正是可迁移信息。

两者都需要额外计算，因此收益必须连同尝试预算看。更多尝试本身也会提高成功率，不能把全部提高归为记忆表示。

<a id="s6"></a>

## 6. 一个数据库排障教学例子

第一次任务中，Agent 看到 CPU 不高就否认性能瓶颈，后来发现大量连接等待。完整轨迹包含查询命令、返回值和时间。提炼出的策略应当是：“请求超时而 CPU 不高时，仍应检查排队、连接池和外部依赖，不能仅凭 CPU 排除资源问题。”

下一次类似任务先检索到该策略，Agent 就会更早补查相关指标。若后续发现这个场景其实是网络故障，经验仍然可以成立，因为它建议增加检查，而没有断言唯一根因。

这说明好的经验往往描述检查顺序与判断边界，而不是把某个具体结论推广到所有故障。

<a id="s7"></a>

## 7. 从一条轨迹中提炼什么，才可能迁移

看一条自拟的网页操作轨迹：搜索订单、打开第一个结果、修改地址、提交，最后发现订单属于同名的另一位用户。如果只保存动作序列，下一次甚至可能复用错误流程。

ReasoningBank 希望提炼的是决策经验：名称相同不足以确认对象，修改前应交叉核对唯一标识和上下文。[1，§3.2] 这个条目可以有如下内容。

| 字段 | 示例 |
| --- | --- |
| 标题 | 修改前核对对象身份 |
| 描述 | 搜索结果可能包含同名对象时使用 |
| 内容 | 先核对订单号或其他唯一标识；无法确认时继续查询，避免仅凭排序第一或名称相同直接修改 |

描述让系统知道何时检索它，正文则给出具体判断步骤。相比“注意谨慎操作”，它指出了触发条件和下一步；相比保存全部页面文本，又去掉了偶然的布局与名称。

经验抽象也可能过头。一次页面响应慢，不能被总结为“所有提交按钮都应点击两次”。更好的经验是先检查状态变化，再决定等待、重试或查错。它保留了观察与决策之间的关系，而不是固定重放动作。

<a id="s8"></a>

## 8. 自评结果怎样影响记忆质量

任务执行结束后，模型根据轨迹代理判断成功与失败，再采用相应方式提取经验。测试时不读取标准答案，使系统能够在缺少逐题人工反馈的环境里继续积累；代价是记忆质量依赖自评是否可靠。[1，§3.2]

如果错误订单已经被修改，但轨迹只显示“提交成功”，裁判可能把任务判为成功。它随后提炼出的成功经验就会遗漏身份核对这一关键步骤。后续任务再次引用它，可能重复同样的错误。

因此，观察到外部接口成功并不等于用户目标完成。任务级评价需要把对象、结果和约束一起检查。论文提供代理自评的循环，实际系统若能获得更可靠的结果信号，应保留并利用它们。

<a id="s9"></a>

## 9. 多次尝试怎样给经验增加对照

MaTTS 同时增加当前任务的尝试和未来可用的经验。两种收益必须分开：多做几次可能直接提高本题成功率；把其中的规律留下来，才可能提高后续任务表现。[1，§3.3]

例如，五条自拟轨迹中，三条在操作前核对对象 ID 后成功，两条仅按同名标签操作而失败。对比可以支持“同名对象存在时先核对 ID”的策略。但它仍可能忽略其他差别，例如成功轨迹也恰好选择了正确区域；多条经历不等于严格控制变量。

如果要识别额外计算与记忆的作用，可以采用下面的对照。它是本文建议的分析设计，不是额外声称作者已经报告了所有单元：

| 配置 | 当前任务尝试预算 | 是否为后续任务保留经验 |
| :--- | :--- | :--- |
| A | 单次 | 否 |
| B | 多次 | 否 |
| C | 单次 | 是 |
| D | 多次 | 是 |

A 与 B 的差别主要帮助理解更多尝试的收益；在相同多次预算下比较 B 与 D，才更接近经验积累的附加作用。还需要固定任务顺序和初始库，避免 D 在更容易的顺序中积累到更有用的经验。

论文的并行方式提供同题多轨迹，顺序方式提供反思修正过程。值得保存的是可复用的判断条件，不是把全部尝试原样堆入提示。若条目只写“做事前仔细检查”，既不能说明从失败中学到了什么，也很难检验它是否帮助下一任务。

<a id="s10"></a>

## 10. 跨任务评测需要留意顺序

一个经验库先做过许多购物任务，再测试相似购物任务，和先做完全无关任务，会遇到不同的检索条件。任务顺序、领域重复程度及初始库状态，都可能影响表现。

对自己的 Agent，我会分别观察经验刚加入之后、被多次使用之后，以及环境变化之后的效果。尤其要保留哪些条目导致退步：一条写得清楚但适用范围错误的经验，比毫无关系的条目更容易误导模型。

这也是简单追加最终需要扩展的地方。除了收集经验，还需识别重复、冲突和过期内容。ReasoningBank v1 把这部分保持简单，有助于研究经验表示；长期服务则需要补上条目的修订与退役机制。

<a id="s11"></a>

## 11. 实验如何验证跨任务价值

论文使用 WebArena、Mind2Web 和 SWE-Bench-Verified，比较无记忆、原始轨迹式记忆、工作流式记忆与 ReasoningBank，并同时报告任务成功与交互步数。[1，§4.1]

WebArena 的一组结果：

| 基础模型 | 无记忆成功率 | ReasoningBank 成功率 | 无记忆／加入后平均步数 |
| --- | --- | --- | --- |
| Gemini-2.5-Flash | 40.5% | 48.8% | 9.7 ／ 8.3 |
| Gemini-2.5-Pro | 46.7% | 53.9% | 8.8 ／ 7.4 |
| Claude-3.7-Sonnet | 41.7% | 46.3% | 8.0 ／ 7.3 |

这支持经验提炼能够同时改善完成率和执行效率。但任务顺序、领域重合、模型与运行配置都会影响收益；它不是任何业务数据上的通用保证。[1，Table 1]

MaTTS 在 WebArena-Shopping 的专门实验中，将并行扩展从 k=1 增到 k=5 时，成功率由 49.7 到 55.1；顺序扩展达到 54.5。它说明记忆与扩展计算可以配合，但也必须与相同预算的扩展基线比较。[1，§4.3]

<a id="s12"></a>

## 12. 为什么自评是主要风险

系统用自己的判断决定哪些经历成功。若失败被误判成功，错误策略就可能进入库；如果后续又检索到它，错误会再次得到机会。流畅的语言表述并不能证明策略可靠。

本文的工程分析是，应把原始轨迹、代理评价和提炼策略分开保留，观察策略在后续任务中的真实表现。否则“库越来越大”很容易被误认为“能力持续变好”。

## 项目实现与数据

> 实现与资源核查：2026-10-24。下面区分论文实验与后续项目演进；本节完成了资源与源码核查，未重新运行作者实验。

### 作者发布了两类任务的实现

[Google Research 的 reasoning-bank](https://github.com/google-research/reasoning-bank)提供 WebArena 网页任务与 SWE-Bench 软件修复任务的代码。它依赖实际任务环境：网页任务需要 BrowserGym 及相应站点，软件修复建立在 mini-swe-agent 等工具之上。只获得一份“经验 JSON”不足以重现实验，还要能重新执行任务并判断结果。

### 从轨迹到经验，代码怎样组织

WebArena 目录中，`pipeline_memory.py`、`induce_memory.py` 与 `memory_management.py` 分别提供阅读执行流程、经验提炼和记忆选择的入口；`autoeval` 保存轨迹自评逻辑。MaTTS 的相关入口则在 scaling 脚本中。具体以[仓库目录](https://github.com/google-research/reasoning-bank/tree/main/WebArena)为准。

理解数据流时，可以把一次任务留下的内容分为三层：实际点了什么、看到了什么；系统如何判断成败；最后提炼成哪条策略。假设网页显示“保存成功”，但修改的是另一个同名对象，自评若只看成功提示，提炼出的经验就可能掩盖错误。排查时需要回到轨迹与对象标识，不能只读最终那条很有道理的策略。

### 数据来自任务，记忆来自运行

官方说明从 WebArena 原始任务配置生成实验输入，也提供修正过部分标注和环境行为的副本；SWE-Bench 则对应代码仓库中的修复任务。ReasoningBank 中积累的策略是运行后生成的派生数据，而不是一份与环境无关的万能记忆训练集。

复现需保存任务顺序、初始记忆、每次纳入的经验、模型与尝试预算。任务顺序会决定前面哪种经验能够帮助后面任务；用未来任务生成的经验再回头测前面的任务，已经改变了“逐步积累”的条件。

当前仓库有后续工程修正，本篇主体仍依据已标明的论文版本。比较新运行结果时，应同时记录环境修正与代码版本，不能把修复网页操作带来的改善全部归因于记忆策略。

<a id="s13"></a>

## 13. 总结与看法

ReasoningBank 研究的是经验表示：把成功与失败轨迹压成可检索的策略，让后续任务使用。它的内容通常比完整日志短，又应比“认真检查”之类通用忠告具体。

值得选读的是抽象的尺度。保留某页面按钮坐标，迁移很弱；只保留泛泛原则，指导性也弱。更有用的条目应说明何时检查、检查什么、根据结果怎样改变操作。失败经验尤其需要保留适用条件，不能从一次失败推出永久禁令。

MaTTS 增加了可比较的经历，但也增加了计算，不能把提升都归给记忆。v1 的纳入过程相对简单，有利于观察经验表示，却不是一套已经解决去重、冲突和过期的长期治理系统。

对经常重复相似任务的 Agent，这篇值得深入方法与对照。真正的验收应是后续任务有没有减少特定错误，并追踪哪些条目造成退步；经验库越来越大并不等于系统越来越会做事。
