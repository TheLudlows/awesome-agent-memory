## “谁负责项目 A”与“这一年主要卡在哪里”不同

前一个问题可能有一份直接答案。后一个问题需要浏览很多项目记录，发现反复出现的主题、关联与差异。即使最相关的五段都谈资源不足，也不能证明资源不足代表整个资料库的主要问题；可能只是这种说法更容易与问题匹配。

微软这篇 GraphRAG 论文主要针对全局理解与查询导向总结。它先组织整个 corpus，生成社区级摘要，再在查询时综合这些摘要。[1，§3]

因此，学习它时不要把“图检索”自动等同于“多跳问答”。图可以用于沿实体关系找证据，而这篇论文特别强调图的社区结构如何帮助覆盖整批资料。

<a id="s2"></a>

## 从文本中提取哪些东西

首先把资料切块，再用 LLM 提取实体、实体间关系以及描述。根据任务也可以提取 claims，记录与实体有关的事件或事实。多个文本块中重复出现的实体和关系被汇总，形成图索引。[1，§3.1]

例如项目 A、团队甲、共享组件 B 可以成为实体；负责、依赖、发生故障等描述建立联系。一个实体在不同文档里可能有不同表述，合并后还需要对描述做归纳。

原文讨论了实体匹配的具体假设。不要仅凭流程图就认为系统已经可靠解决别名、同名对象和时态冲突。把两位同名人员合成一个节点，可能让后面的社区和摘要一起偏离。

<a id="s3"></a>

## 社区不是预先写好的分类目录

图建立后，论文用层次化 Leiden 社区检测寻找连接较紧密的节点组，再进一步形成更细的子社区。一个社区可能围绕某项业务、某类技术或一组相互协作的团队。[1，§3.1.4]

这类分组依据图结构，而不是人工先设定“成本”“性能”“稳定性”几个标签。随后为社区生成报告式摘要，聚合实体、关系及相关事实；高层社区在必要时使用低层摘要来控制上下文大小。

这样，系统获得了一组能够覆盖语料不同区域的概括。它们在查询到来前就已经生成，可以供多个问题复用。但社区划分质量依赖抽取出的图，错误实体和关系不会因为做了聚类就自然消失。

<a id="s4"></a>

## 全局查询怎样利用这些摘要

针对一个社区层级，论文将社区摘要整理成若干上下文批次，并行生成针对当前问题的中间答案，同时评估各答案的帮助程度。过滤没有帮助的结果，再按优先级汇总，在上下文预算内生成最终答案。[1，§3.1.6]

可以把它理解为先让多组资料分别回答同一个问题，再综合它们。它不是简单地选几个最近的实体，也不要求把整张图原样放进提示词。

这种 map-reduce 式流程扩大了资料覆盖，但帮助程度评分依旧由模型产生。一个少见却重要的风险可能被低估；多个社区重复提及同一事件，也可能让它看起来比实际更普遍。

<a id="s5"></a>

## 用项目复盘理解它的收益与边界

假设有 300 份项目周报。普通片段检索回答“这一年交付延迟的主要原因”时，可能只拿到几篇最像复盘报告的文档。GraphRAG 可以先形成围绕平台依赖、供应资源和上线流程的社区，再分别总结原因，最后比较共同因素。

这里的收益是覆盖和关联，不是自动生成精确统计。如果回答说“60% 的项目因为资源不足延期”，就需要可计算的项目口径、去重和原始记录，不能把语言模型读摘要后的感觉当作统计结果。这个例子中的数量是教学设定，不是论文实验数据。

对于业务知识库，结构化统计与总结生成可以配合：先用确定性计算得出比例，再让模型解释相关证据。论文的全局总结不替代数据库聚合，也不自动解决权限范围下的图构建与查询。

<a id="s6"></a>

## 论文怎样评估全局答案

论文围绕全局 sensemaking 设计问题生成与评价，比较答案的全面性、多样性等维度，并使用 LLM 比较不同方案的输出，还通过提取可验证陈述进行补充分析。[1，§3.2、§4]

这些评价适合没有单一短答案的归纳任务，但与 NQ 的 Exact Match 或 BEIR 的 nDCG 不同。一个答案更全面、更受裁判偏好，不自动证明其中每个事实都正确，也不说明图方法在所有精确事实查询上优于普通 RAG。

阅读时应特别关注比较对象是否使用相同模型和预算，以及社区摘要相对直接文本总结的贡献。单看“图方案胜率更高”，容易忽略预处理已经进行了大量抽取与摘要生成。

## 项目实现与数据

[microsoft/graphrag](https://github.com/microsoft/graphrag) 提供完整索引与查询项目，文档入口在 [官方站点](https://microsoft.github.io/graphrag/)。原文和项目包含的能力范围会随版本变化，当前项目的 local、global 或其他查询方式不应全部归为这篇原论文的同一算法。[2]

阅读代码时，优先追踪几个中间产物：text units、entities、relationships、communities 和 community reports。它们分别对应原文、抽取结构、分组以及生成摘要。理解这些表之间的来源关系，比先熟悉所有命令行参数更有用。

这类项目通常允许使用自己的文档，不能把官方代码开源等同于所有论文实验语料都以完整可复现形式随代码提供。需要按论文的数据说明和发布资源分别核对。本篇没有运行全量索引，也没有复现论文胜率。

工程成本主要集中在抽取、摘要和更新传播。新增一份文档可以影响实体描述、社区结构和报告内容；如果资料经常改变，需要单独验证更新策略与重建预算，不能仅参考一次静态构建的开销。

<a id="s8"></a>

## 总结与看法

GraphRAG 值得学习的地方，是对“全局问题”给出了与局部相似检索不同的处理方式。先覆盖语料、组织主题，再面向问题汇总，能够帮助系统看见散落在不同文档中的联系。

我会在调研、复盘和跨文档归纳需求明确时考虑它；若主要查询是错误码、配置项和单个接口行为，应先把直接检索做好。图和社区摘要都是有价值的派生信息，但应保留来源并控制生成成本。对全局理解的改善，需要用相应任务来证明。
