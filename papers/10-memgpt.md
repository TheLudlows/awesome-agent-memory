# MemGPT：MemGPT：迈向作为操作系统的大语言模型

**英文题名：** MemGPT: Towards LLMs as Operating Systems

**版本与时间：** 2023  
**主题：** 上下文管理  
**原文入口：** [主文](https://arxiv.org/abs/2310.08560) · [arXiv](https://arxiv.org/abs/2310.08560)  
**核对日期：** 2026-10-23  
**阅读依据：** [正文或技术版本](https://arxiv.org/pdf/2310.08560)；涉及补充稿的内容单独说明。本文为首版通俗解析，不包含独立实验复现。文中的教学例子与“本文推论”不是论文原始实验。

## 一句话理解

模型上下文像有限大小的工作台，外部存储像仓库。MemGPT 给模型搬运工具，让它决定什么时候去仓库找材料、把什么留在工作台上。[1]

## 它解决什么问题

历史越长，全部放入 prompt 越不现实。即使数据保存在外面，模型也不能自动看见；必须有调度机制把需要的内容送进当前上下文。

## 核心设计

论文区分上下文内的 main context 与上下文外的 external context。主上下文包含系统指令、可修改的工作区与 FIFO 消息队列；外部存储保存可检索的历史和归档信息。模型通过函数调用读写记忆，系统借助事件和内存压力等信号管理控制流。[1，§2]

这里的“虚拟上下文”不是把模型的真实窗口变成无限长。每次推理能直接看到的仍然是窗口内的内容，窗口外的信息必须先取回来。

## 教学例子：一段超长项目历史

工作区保留当前目标、约束与阶段结果；历史日志放在外部。用户问“上次为什么否决方案 B”，Agent 搜索历史、取回相关证据，再回答。读取更多材料也可能需要多轮工具调用。

与普通的一次 top-k RAG 相比，重点是 Agent 能参与决定何时调入什么信息。

## 实验说明什么

论文在长文档分析与多会话聊天中检验方案，展示有限窗口配合外部存储的能力。[1，§3] 这并不保证模型总能主动想起该搜索什么，也不保证所有长期信息都能无损恢复。

## 对基础设施的启示（本文推论）

上下文管理应有预算、溢出处理和可观察的工具调用轨迹。长期记忆可提供搜索、分页读取与局部修改能力，但工具返回不能无限扩大。关键约束最好有确定性保留规则，避免完全依赖模型临时决定是否搬走。

## 与 MemoryOS 的关系

MemGPT 重点是上下文内外的主动调度；MemoryOS 重点是对话记忆的层次与晋升。操作系统是设计类比，两者都不是在论文里实现了真正的通用操作系统。
