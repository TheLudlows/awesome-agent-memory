## 1. 有限窗口怎样处理超过窗口的信息

一本长书可以放在硬盘上，但模型每次只能读有限 token。数据“存在外面”并不会自动参与推理，必须把需要的部分搬进当前输入。

MemGPT 把这个问题类比为操作系统中的内存与外部存储：主上下文相当于工作内存，历史与归档相当于容量更大的外部空间，函数调用负责搬运。它称为虚拟上下文管理，提供超出固定窗口的访问能力。[1，§2]

“无限上下文”是系统能力的类比，不是 Transformer 一次真的同时注意无限文本。每次推理看见的仍是当时放入窗口的内容。

<a id="s2"></a>

## 2. 主上下文分成哪几部分

### 系统指令

说明模型的身份、控制方式、记忆层次和可调用函数。这部分相对固定，告诉模型怎样使用记忆系统。

### 工作区

一个有限、可修改的文本区域，用于保存必须随时可见的事实与当前目标。例如用户偏好、正在推进的任务状态。它不同于无限增长的聊天历史，因为容量有限，需要选择。

### FIFO 消息队列

保存最近的消息与事件。随着新输入到来，旧内容会离开活跃窗口，并通过总结或外部历史保持可访问性。队列支持连续交互，但不能单独承担长期细节记忆。[1，§2.1]

<a id="s3"></a>

## 3. 外部存储为什么区分历史与归档

**Recall storage** 保存可检索的历史消息，适合找“以前具体说过什么”；**Archival storage** 保存更通用的知识或被归档的信息，适合容纳文档与长期内容。它们都在当前窗口外，需要显式读取。

这与“把所有内容都浓缩进用户简介”的设计不同。MemGPT 可以保留精简的常驻工作区，同时让细节仍然通过搜索可用。工作区是长期信息的选择性投影，不应被当成完整原始历史。[1，§2.2]

<a id="s4"></a>

## 4. 模型怎样管理自己的上下文

函数执行器接收模型提出的调用，检查参数后执行，把结果或错误送回当前上下文。工具可以搜索历史、读取归档、修改工作区等。

模型接近上下文上限时，系统提供内存压力警告；检索结果分页返回，避免一次搜索又把窗口塞满。如果模型试图写入超限内容，执行错误也会成为反馈。

因此，这种自主性是“模型在规定接口和预算中做调度”，并不意味着绕过程序约束任意改变运行时。[1，§2.3]

<a id="s5"></a>

## 5. 控制流为什么需要连续函数调用

一次任务可能需要搜索多个页面、根据第一条记录继续查第二个对象、再综合回答。如果每次工具调用都立即把控制权交还用户，系统就无法独立完成这些小循环。

MemGPT 允许函数调用后请求继续运行，让工具结果成为下一次推理的输入；也允许暂停，等待用户消息或下一事件。系统事件可以包括用户输入、容量警告、上传完成和定时事件。[1，§2.4]

可以把它理解为：工具调用不只是返回资料，还参与决定“下一步继续想，还是现在结束”。这一点使记忆管理成为 Agent 控制流的一部分。

<a id="s6"></a>

## 6. 用一段跨多天的对话走一遍

第一天用户说生日是 2 月 7 日。模型决定把它写入工作区。后来很多聊天挤掉了早期消息，但生日仍可能常驻；一些低频细节则留在外部历史。

用户再问“上次去的那个游乐园叫什么”，模型搜索历史，看到分页结果，必要时继续翻页；找到证据后更新当前理解，再回答。如果关系状态后来改变，也可以修改工作区中已经过时的常驻描述。

论文包含类似的长期对话情境。这里最值得理解的是信息路径：历史保存不等于常驻可见，常驻可见也不等于永远正确，模型需要主动读取和修订。

<a id="s7"></a>

## 7. 容量警告出现之后，一次“换页”怎样进行

容量管理由模型与程序共同完成，不能理解成模型自己决定何时清空历史。论文中的 Queue Manager 跟踪 token 数，达到 warning 阈值时插入容量警告；达到 flush 阈值时执行队列淘汰。文中以窗口的 70% 和 100% 举例，这不是所有实现必须固定采用的比例。[1，§2.2]

警告给模型一个机会：把仍需常驻的信息写进工作区，或将有用内容归档。真正腾出窗口时，队列管理器移除一批较早消息，用“已有递归摘要＋本次移出的消息”生成更新后的摘要，放在队列前部。原始消息仍在 recall storage 中，后续可以搜索找回。

以下是自拟状态变化，省略具体 token 数和接口名：

| 时刻 | 当前窗口 | 外部历史 | 谁触发变化 |
| :--- | :--- | :--- | :--- |
| 接近容量上限 | 排障目标、大量工具结果、近期对话 | 已保存消息记录 | 程序插入警告 |
| 模型处理警告 | 工作区补充“已排除连接数上限” | 可另行归档需要的内容 | 模型调用写入工具 |
| 执行淘汰 | 递归摘要与剩余近期消息 | 被移出的原始消息仍可搜索 | 队列管理器 |
| 后续追问某次采样值 | 搜索结果重新进入窗口 | 读取相应历史片段 | 模型选择查询，程序执行 |

这与操作系统换页有一个关键差异：摘要不是原始内容的无损副本。被移出的消息可以在外部完整保留，但模型不会像访问虚拟地址那样自动获得正确页面。它要先意识到缺少信息，再生成能够找回证据的查询。

所以，“窗口不溢出”是程序能保证的容量属性，“重要内容以后还能被正确使用”却取决于保存、摘要和查询的配合。把两者混为一谈，会高估虚拟上下文这个类比。

<a id="s8"></a>

## 8. Heartbeat 如何让模型继续查，而不是提前结束

Heartbeat 解决的是一次工具执行之后是否立即再调用模型。模型在函数调用中请求继续，执行器把工具结果送回上下文，随后触发下一轮推理；不必等用户再说一句“继续”。[1，§2.3–§2.4]

看一个自拟的键值链：A 的值是 B，B 的值是 C，C 才指向终值 42。每次工具调用都成功，但前三次拿到的信息性质不同。

| 模型轮次 | 已看到什么 | 应做什么 |
| :--- | :--- | :--- |
| 1 | 用户要求求 A 的终值 | 查询 A，并请求继续 |
| 2 | A → B | 查询 B，并请求继续 |
| 3 | B → C | 查询 C，并请求继续 |
| 4 | C → 42，已满足任务约定的终止条件 | 回复 42，结束本次执行 |

工具只负责返回数据，不会自动判断“B 还是一个待查询的键”。判断和下一次调用由模型完成，heartbeat 则让这个判断有机会发生。这就是它与固定“搜索一次，然后生成答案”流程的区别。

多轮调用本身并不保证正确。模型可能把 B 当最终答案，也可能取到 42 后还重复查询。因此应检查调用轨迹中的两个决策：什么时候继续，什么时候停止。论文的嵌套键值任务正是用需要连续访问的情形来观察这种能力，而不是把单次检索准确率当作全部表现。

对于本来就能用确定循环处理的键值链，普通程序当然更直接。这个实验的意义在于展示模型驱动的连续访问能力，不是说明查链表应该交给 LLM。

<a id="s9"></a>

## 9. 检索接口为什么要分页

搜索返回一百条相关记录，并不代表主上下文装得下。分页允许模型分批读取，并据此决定是否继续。这样查询预算可以随着任务需要增加，而不必一次把全部候选塞进窗口。

代价是控制步骤增多。若答案位于很后面的页面，模型需要付出多次调用；若查询过宽，还可能把大部分时间花在无关结果上。所以分页解决容量溢出，不自动解决检索质量和调用成本。

原论文的长期对话实验表明，外部历史可以恢复被窗口排除的早期信息。嵌套查询则更强调连续访问能力。这两种结果分别说明“有地方保存”和“有机制反复读取”的价值，不能只归结为换了一个更好的向量搜索器。

如果要把这种调度用于实际业务，我会为常驻约束、普通历史和待验证线索设置不同管理方式。明确的执行限制可以由程序强制提供；探索性证据交给模型按需读取。这样既保留自主查询，也减少把关键规则完全交给模型记忆选择的风险。

<a id="s10"></a>

## 10. 实验怎样证明虚拟上下文有价值

### 长期对话

论文使用 Multi-Session Chat 相关设置，测试能否找回早期交互细节，以及能否利用长期背景维持交互一致性。深层记忆检索 DMR 的报告结果包括：

| 基础模型 | 固定上下文准确率 | 加入 MemGPT |
| --- | --- | --- |
| GPT-3.5 Turbo | 38.7% | 66.9% |
| GPT-4 | 32.1% | 92.5% |
| GPT-4 Turbo | 35.3% | 93.4% |

这些数值说明在该历史访问任务中，外部记忆能缓解固定窗口丢失证据的问题，不代表所有普通问题也会得到同样提升。[1，§3.1，Table 2]

### 文档与多步查询

作者还测试多文档问答和嵌套键值查询。后者不是“查一次键就结束”，而是一个值可能又指向下一个键，需要连续查找。实验观察到，仅靠窗口内一次阅读的模型更容易提前停止；使用工具连续读取的 MemGPT 更能完成查找链。[1，§3.2]

这个任务强调调度与多轮操作，不只是检索模型本身是否准确。

<a id="s11"></a>

## 11. 这种方法有什么代价

模型需要正确判断该搜什么、何时继续和何时停止。更多工具调用会增加延迟，也可能出现无效循环。若常驻工作区被错误覆盖，长期错误会影响后续交互；若历史搜索漏召回，外部保存再完整也无济于事。

论文时代的窗口大小与模型能力有历史背景。今天更长的窗口不会让管理问题消失，但会改变直接读取与主动检索的成本平衡。不能照搬当时模型能力限制作为永恒前提。

## 项目实现与数据

> 实现与资源核查：2026-10-24。下面区分论文实验与后续项目演进；本节完成了资源与源码核查，未重新运行作者实验。

### MemGPT 的开源项目后来去了哪里

[论文研究主页](https://research.memgpt.ai/)链接代码和实验数据。MemGPT 项目后来发展为 Letta；截至本次核查，[letta-ai/letta](https://github.com/letta-ai/letta)的 README 将当前实现指向 `letta-ai/letta-code`，历史 Letta V1 服务端保存在 `archive` 分支。`archive` 也不自动等于 2023 论文版本，严格复现还需核对历史提交或发布标签。

读当前产品可以理解状态化 Agent 如何应用，读原论文则应追踪主上下文、外部存储、工具调用及控制循环。两条路线有关联，但最新终端界面或 App Server 的功能不能倒推为原论文已有的能力。

### 论文相关数据长什么样

研究主页链接的 MemGPT 数据空间中，可以找到 [MSC-Self-Instruct](https://huggingface.co/datasets/MemGPT/MSC-Self-Instruct)和 [qa_data](https://huggingface.co/datasets/MemGPT/qa_data)。前者展示人物设定、当前对话、此前会话及 `self_instruct` 等结构，适合检查跨会话回忆；后者包含 `question`、`answers`、候选上下文 `ctxs` 与参考证据，用于文档问答。

可以把前者想成一份连续聊天档案，后者想成“问题加一批待查阅资料”。它们需要的访问方式不同：聊天要找回某个人之前说过什么，文档任务要从大量候选资料中找到答案。数据平台显示的 `train` split 名称只是发布组织方式，不能据此断定论文对模型做了参数训练。

### 怎样观察虚拟上下文是否工作

做一个小实验时，先写入几段历史，再提出必须查询较早记录的问题，保存完整工具调用轨迹。重点看模型有没有发现信息不在当前窗口、是否调用搜索、结果不够时是否继续翻页，以及找回的信息何时被用于回答。

如果它只是碰巧凭模型常识答对，不能证明外部记忆发挥作用；如果找到了证据却没有正确作答，问题可能在上下文组织或阅读。复现应同时记录窗口上限、分页大小和工具调用预算，避免把更大的预算误认为调度机制本身的收益。

<a id="s12"></a>

## 12. 总结与看法

MemGPT 值得精读的是执行协议：哪些信息常驻，哪些移到外部，谁处理窗口溢出，模型调用工具后怎样继续。这些细节决定记忆是否真正进入后续决策，操作系统的比喻只是帮助理解。

最有用的设计分工是，程序管理容量和接口，模型选择读写内容。窗口满了，程序可以确定地淘汰；用户追问旧细节时，却仍需模型判断该搜什么。外部保存完整历史，因此不同于只剩摘要；但搜索和阅读都可能失败，也因此不能称作无损的无限上下文。

DMR 的结果支持它能找回被固定窗口排除的旧信息，嵌套键值任务支持连续访问的作用。这些结果没有单独证明每一种工作区设计都最优，也没有说明在相同总调用预算下，它对所有任务都优于固定检索流程。

对需要持续调查、根据新证据改变查询方向的 Agent，这篇很有参考价值。对一轮搜索就能回答的问题，多轮调度可能只增加等待。实现时应先保留清楚的状态边界和调用轨迹，再决定哪些查询值得交给模型自主展开。
